# 现状调研文档索引（surveys）

> 本目录收录对本项目**现有功能/子系统现状**的系统性梳理文档。
> 目的：在动手优化或扩展之前，先把「现在到底是怎么实现的、能看到什么、强在哪、短在哪」固定成文，避免每次改动都重走一遍代码。

---

## 这份目录解决什么问题

本 fork 以「新增能力」为主，改动前必须先理解上游现状，否则容易：

- 重复造轮子（已有机制没发现）；
- 改错层（本该新增模块，却深改核心）；
- 误判能力边界（把「参数复杂」当成「不支持」，或反之）；
- 被散落的隐式规则坑到（三套 scope 判定、两种参数视图之类）。

**surveys 目录 = 改代码前的地图。** 每份文档对应一个子系统或一组功能，目标是把现状讲到「看一遍就能定位改动点」的程度。

## 与相邻目录的区别

| 目录 | 放什么 | 不是用来干什么 |
|---|---|---|
| `docs/fork/surveys/`（本目录） | **现状梳理**：现有机制怎么运作、能力边界、短板 | 不写需求、不写改造方案 |
| `docs/fork/` | 具体功能的**需求文档 + 实现状态/交接**（如 `function-workflow.md`） | 不负责全局机制拼图 |
| `docs/`（上游） | 上游既有的架构/规范/API 文档 | 上游文件，尽量不动 |

> 判断标准：**「描述现在是什么样」→ surveys；「记录某个功能要做成什么样」→ `docs/fork/`。**

## 写作规范（后续新增梳理文档时请遵循）

### 结构约定

1. **开头写清四件事**：版本、对应分支/日期、目录归属（fork 独有 → 冲突归我方）、用途。
2. **先给总览**：这个子系统有哪几块、彼此什么关系（尤其容易混淆的「多套并行实现」要开篇点破）。
3. **再逐块展开现状**：机制、入口文件、关键行号、边界条件。
4. **事实与评估分开**：事实描述附代码位置；主观的「强/弱/可优化」集中到独立小节（如 `§2.10 能力与现状评估`），明确标注是判断而非事实。
5. **结尾给落点**：改这类东西应该动哪里、有哪些现成的坑（扩展落点 / 优化方向）。

### 硬性要求

- **所有行号必须回代码验证**，不要凭记忆或推测。文档一旦行号漂移，可信度就崩了。
- **数字（模块数、工具数、技能数等）必须实测**。若无法自动统计，在文中注明「人工走查，会随代码漂移，引用前以代码为准」。
- **区分「事实错误」与「过时」**：走查发现旧文档错误时，在修订记录里写清是「原文写反」还是「代码已变」。
- **每处与上游的分歧，同步登记到 `FORK.md`**（对照其「与上游的分歧清单」表格）。

### 命名约定

- 文件名用 `<子领域>-<类型>.md`，类型为 `overview`（体系梳理）或 `survey`（单点调研）。
- 例：`ai-system-overview.md`、`workflow-engine-overview.md`、`module-system-overview.md`。
