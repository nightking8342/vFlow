## 1. 为什么要先做这个

### 1.1 对用户：采集日志调试触发器

调试 logcat 触发器的工作流是「复现 → 看日志 → 试条件」。没有工具时用户只能：
猜 TAG 名、猜消息格式、猜多行日志长什么样。本工具把这三件事变成可见、可试。

### 1.2 对开发：提前消化触发器设计的风险

| 触发器设计的风险项 | 本工具能否提前消化 |
|---|---|
| §5.1 解析 / 降级语义 | ✅ **能**——同一份纯函数在真实日志上先跑通 |
| §6.4 `-T 1` / `-c` 缓冲问题 | ✅ **能**——实测确认 |
| §9 风险 3「Core 跑长驻进程稳定性」 | ⚠️ **部分**——本工具的采集就是一个长驻 logcat 进程，先验证存活与清理 |
| §6.5 双工协议（**最贵的未解项**） | ❌ **不涉及**——本工具全程走 request/response，见 §3 |

**结论**：本工具能让触发器项目在开工前把「解析对不对、进程稳不稳」问清楚，
只把「双工协议」留给触发器本身。

## 2. 关键约束（决定了方案形态）

### 2.1 ⚠️ 两条 shell 通道都有传输上限（**已实测证实**）

| 通道 | 实现 | 瓶颈 |
|---|---|---|
| Shizuku 直连 | `IShizukuUserService.exec(command): String`（`IShizukuUserService.aidl:21`） | 返回值是 **Binder Parcel**，IPC 事务上限约 **1MB**；实现里是全量读进 String 再返回（`ShizukuUserService.kt:65-110`） |
| 经 Core | `sendRaw` + `JSONObject`（`VFlowCoreBridge.kt:524-554`） | 无非天然上限，但 `output` 要**转义进 JSON**，几 MB 日志会膨胀数倍 |

**结论：不能一次性把全量日志拉回来。** 这是方案约束，不是优化项。

**对策**：**跨进程传输的数据量必须由 shell 侧决定**——
用 `logcat -T <n>` 或 `tail -n <n>` 限制，让同一时刻在途的数据有硬上限。

> ✅ **实测证据**（2026-09-17，探针首轮）：裸跑 `/system/bin/logcat -d -v threadtime`
> （全量缓冲区）时，Shizuku 侧直接抛出：
>
> ```
> android.os.DeadObjectException: Transaction failed on small parcel;
> remote process probably died, but this could also be caused by
> running out of binder buffer space
> ```
>
> UserService 被打死，整条通道需要重连。**这条从"推断"变成了"实测"。**

### 2.1b ⚠️ 后台进程必须切断 stdio，否则 `exec` 永久挂起（**已实测证实**）

**这条比 §2.1 更隐蔽**：它不报错、不抛异常，只是**静默挂住**。

`ShizukuUserService` 读输出的方式是**读到 EOF 才返回**：

```kotlin
val stdout = readStream(process.inputStream)   // 阻塞直到 EOF
val exitCode = process.waitFor()
```

而 `sh -c "... &"` 启动的后台进程会**继承 shell 的 stdout**。于是：

```
shell 退出 → 后台 logcat 仍活着 → 管道不关闭
           → readStream 等不到 EOF → 整个 exec 永不返回
```

**对策：后台命令必须完全切断三个 stdio**：

```bash
# ❌ 挂死
logcat ... -f $FILE & echo $! > $PIDFILE

# ✅ 正确
logcat ... -f $FILE >/dev/null 2>&1 </dev/null & echo $! > $PIDFILE
```

> ✅ **实测证据**（2026-09-17，探针第二轮）：未切断 stdio 时，
> 日志停在启动命令之前，之后**一条输出都没有**——探针挂死在工作流里，
> 用户只能手动停止。加上重定向后，第四轮跑通（见 §2.4）。

### 2.2 logcat 的 ring buffer 是有限的 ★（**实测修正**）

> 🔴 **本节 2026-09-17 修正。** 初稿写「默认各只有几百 KB，几秒到几十秒就轮转一圈」——
> **这是错的**。真机实测：

```
C.1 全量缓冲区行数 = 192578   ← root 身份那次
C.1 全量缓冲区行数 = 113888   ← 纯 Shizuku 那次（约一小时后）
```

**缓冲区比初稿的估计大一个量级。** 因此「快照不够用」的论证要重新表述：

| 初稿的说法 | 实测 |
|---|---|
| 缓冲只有几百 KB，几十秒就轮转 | ❌ 十万量级，轮转慢得多 |
| 快照基本不可用 | ⚠️ **比预想的可靠**，但仍有两个真问题（见下） |

**两次测得不同值（19.2 万 / 11.4 万），这本身是关键信息**：
`C.1` 拿到的是**滚动窗口的当前存量，不是容量上限**。
存量随设备活动波动——安静时更多、繁忙时更少。

**快照仍然不能作主路径，但理由变了**——不再是「缓冲区太小」，而是：

1. **余量不可预判。**
   存量随日志密度波动，用户**无法知道当前还剩多少**。
   在日志风暴（崩溃循环、频繁的 `ActivityManager` 输出）下，十万行可能几分钟就冲完。
2. **失败方式仍然是静默的。**
   缓冲区被冲掉时不报错，只是返回一段**不含目标日志**的内容。
   用户会误以为「我的日志没打出来」——**静默失败是最贵的失败**。

也就是说：快照在**大多数情况下能用**（比初稿的判断宽松），
但它**给不了确定性**，而调试恰恰需要「我复现了，你一定抓到了」。

**结论（不变）：主路径是「开关式持续采集」，快照作兜底。**
但要按 §4.6 在快照结果里给出**诚实的状态提示**，而不是假定它一定失败。

> ⚠️ **未测**：存量对应的**时间跨度**，以及容量上限本身。
> 要判断轮转风险需要「安静」与「日志风暴」两种负载下的沉降速度，本次没测。
> 若将来要给用户提示「缓冲区大约还能容纳多久」，需要补测。
>
> ℹ️ 另注：`C.1` 的计数里**含日志头标记行**（`--------- beginning of ...`），
> 所以「行数」略高于真实日志行数。差异可忽略，但解析时应跳过这类行。

### 2.3 不需要流式协议

采集改用「shell 侧后台写文件」后，**三条命令全是普通 `exec`**：

| 需求 | 命令 | 是否用到流式协议 |
|---|---|---|
| 启动采集 | `logcat ... -f <file> >/dev/null 2>&1 </dev/null &`（★ stdio 必须切断，§2.1b） | ❌ 普通 request/response |
| 停止采集 | `kill $(cat <pidfile>)` | ❌ 普通 |
| 查看日志 | `tail -n 2000 <file>` | ❌ 普通（且**有界**） |

**收益**：完全绕开触发器设计 §6.5 那套未验证的双工协议，同时天然满足 §2.1 的上限约束
（数据落文件，只有要显示的部分跨进程）。

### 2.4 ✅ 真机实测结果汇总（2026-09-17）

> 用临时探针（`LogcatProbeModule`，验证后已删除）在
> **Xiaomi MIX Fold 3 / Android 17 / HyperOS** 上跑通，完整报告如下。

**环境**：同一台设备跑了**两种执行身份**——这一点很重要，见下。

| | 轮次 A（首测） | 轮次 B（补测） |
|---|---|---|
| `E.1` 身份 | `uid=0(root)` `context=u:r:ksu:s0` | **`uid=2000(shell) groups=...,1007(log),...`** |
| 说明 | Shizuku 由 **KernelSU（root）** 启动 | **纯 Shizuku，无 root** |
| `E.2` | `build.type=user` `ro.debuggable=0` `selinux=Enforcing` | 同左 |
| `E.3` | `default_shell_mode=shizuku` `isShizukuActive=true` `isRootAvailable=true` | 同左 |

⚠️ **注意**：`default_shell_mode` 两次都是 `shizuku`，但实际身份不同——
**设置里的选项不决定实际 uid，由 Shizuku 自身的启动方式决定**。
这正是 `logcat-readability-survey.md` §4.3 那条教训（"标签在说谎"）的再次体现。

**两轮结果对照**：

| 项 | 轮次 A（root） | 轮次 B（纯 Shizuku） | 判定 |
|---|---|---|---|
| `A.1` 对照 TAG 行数 | 2 | 2 | ✅ 通道一致可用 |
| `A.2` 系统 TAG(ActivityManager) | 2254 | 2495 | ✅ 都能读系统日志 |
| **缓冲区规模 `C.1`** | 192578 | 113888 | 见下方说明 |
| `-T 5` / `-t 5` 行数 | 6 / 6 | **7 / 6** | ⚠️ 见下方说明 |
| `-T 20` / `-t 20` 行数 | 22 / 22 | 21 / 21 | ✅ 均为「最近 n 行」+1~2 |
| `-T 1` 首行 | `--- beginning of main` | `--- beginning of main` | ℹ️ 返回的是**日志头标记**，非真实日志 |
| 全量首行 `C.4` | `--- beginning of crash` | `--- beginning of system` | ℹ️ 缓冲按类别分 |
| **后台 `&` 存活** | 1 ✅ | **1 ✅** | ✅ **结论一致** |
| 采集文件行数 `D.4` | 363 | 430 | ✅ 都在写 |
| marker 落盘 `D.5` | 1 ✅ | 1 ✅ | ✅ 都抓到了本 App 日志 |
| pidfile 写入 `D.2` | `pid=6100` | `pid=23831` | ✅ `echo $! > file` 正常 |
| **`kill` 清理** | rc=0 → 存活 0 ✅ | **rc=0 → 存活 0 ✅** | ✅ **结论一致** |
| 轮转文件数 `E2.1` | 3 | 3 | ⚠️ 均比 `-n 2` 的直觉多 1，见下 |
| 全设备 logcat 进程数 `D.3b` | 3 | **1** | ⚠️ 见下（印证该指标不可靠） |

**✅ 核心结论：所有代码级约束在两种身份下都成立。**

| # | 约束 | 两种身份是否一致 |
|---|---|---|
| 1 | Binder 传输上限（§2.1） | ✅ 一致（首轮 `DeadObjectException` 本身就是 root 身份下发生的） |
| 2 | 后台进程须切断 stdio（§2.1b） | ✅ 一致（切了才能活，与身份无关） |
| 3 | 后台 `&` 进程可存活 | ✅ 一致 |
| 4 | `kill` + pidfile 清理链路 | ✅ 一致 |
| 5 | `-T`/`-t` 语义 | ✅ 一致 |
| 6 | 轮转 `-r`/`-n` | ✅ 一致 |

**三个需要解释的差异**：

1. **缓冲区规模 192578 vs 113888**
   这不是身份差异，是**采样时间点不同**——logcat 缓冲是滚动窗口，两次采样间隔的日志量不同。
   实际含义：**缓冲规模是动态的**，`C.1` 拿到的是"这一刻的存量"，不代表容量上限。
   这进一步支持 §2.2 的结论：**用户无法预判余量**。

2. **`-T 5` 得 7 行、`-t 5` 得 6 行（轮次 B 独有）**
   轮次 A 是 6/6。差 1 行的原因应是缓冲区里**混入的日志头标记行数量不同**
   （`--------- beginning of ...`）。这些标记行不是真实日志行。
   **实现时的含义**：不要假定「`-T n` 恰好返回 n 行」，解析时要能识别并跳过标记行。

3. **`D.3b` 全设备 logcat 进程数：3 vs 1**
   这个指标在轮次 A 看到 3、轮次 B 看到 1。
   可能原因：uid=2000 对 `ps` 的**可见性受限**（看不到其他用户的进程）。
   ✅ **这恰好印证了探针设计的判断**——`D.3b` 标注为"仅参照，勿用于判定"是对的，
   真正可靠的是 `D.3`（按 pidfile 精确匹配自己启动的那个）。

**⚠️ 关于轮转文件数 = 3**（两轮一致）：`-n 2` 时期望 ≤2 个文件，实测 3 个。
可能是 `-n` 的语义是「保留的轮转文件数」而当前写入文件不计入，也可能是 ROM 实现差异。
**不影响方案**（上限依然有界），但实现时**不要硬编码文件数**，用 `ls $FILE*` 动态枚举。

**✅ 三条代码级结论从「推断」升级为「实测」**：

1. §2.1 — Binder 缓冲上限（首轮 `DeadObjectException`）
2. §2.1b — 后台进程不切断 stdio 会挂死（第二轮无输出挂起）
3. §2.2 — 缓冲区规模（动态，非固定容量）

**探针自身的教训**（也是调试工具实现时的坑，已写入代码注释）：
- **增量输出**：探针初版把报告攒到最后才打，第二轮挂死时**一条数据都没保住**。
  改成每行即时写日志后，才有完整报告。
- **命令加超时**：超时不该被当成"卡住"，而是**一项观测结果**（标记 `TIMEOUT`）。
- **进程判定要用 pidfile 精确匹配**：`grep logcat` 会把系统进程算进来（假阳性），
  且该指标的可见性**还受执行身份影响**（`D.3b` 两轮差 2）。
- **不要预设执行身份**：设置里写 `shizuku`，实际可能是 `root`（轮次 A 即如此）。

## 3. 方案选型：为什么是「开关写文件」而非其他

### 3.1 被否掉的两个方案

| 方案 | 为什么否掉 |
|---|---|
| **纯快照**（`logcat -d -T N`） | §2.2——复现过程大概率已滚出缓冲区，且**静默失败** |
| **开关 + 实时流到 UI** | 需要 Core 侧 `StreamingWrapper` 双工（触发器设计 §6.5，**未验证**），且受 §2.1 的 1MB 上限约束；只为「边看边滚」的体验引入最高风险项，不划算 |

### 3.2 采纳：开关（shell 侧写文件）+ 快照兜底

```bash
# 开始采集：立即返回，logcat 自己转到后台
# ★ 三个重定向必须加，否则 exec 挂死（§2.1b）
logcat -v threadtime -r 1024 -n 3 -f /sdcard/vFlow/logs/capture.log \
  >/dev/null 2>&1 </dev/null & echo $! > /sdcard/vFlow/temp/logcat_capture.pid

# 停止采集
kill $(cat /sdcard/vFlow/temp/logcat_capture.pid)

# 查看（从文件尾部有界读取）
tail -n 2000 /sdcard/vFlow/logs/capture.log
```

**为什么用 `-r 1024 -n 3`**：这是 **logcat 自带的轮转**（每 1MB 转一次、保留若干份）。
文件**不会无限增长**，因此**不需要自己写清理逻辑**——上限约 3-4MB，天然可控。

> ⚠️ **实测注意**（§2.4）：`-n 2` 时实测得到 **3** 个文件，与「保留 2 份」的直觉不符。
> **实现时不要硬编码文件数**，用 `ls $FILE*` 动态枚举即可。
> 上限依然有界，不影响方案。

### 3.3 两者分工

| 场景 | 用什么 |
|---|---|
| 「我要复现一个问题」 | **开关**——先开，去复现，回来停/查看 |
| 「我就想看现在有什么日志」 | **快照**——一次性抓最近 N 行 |
| 快照结果里**没有**目标日志 | 提示「可能已被轮转，试试开启采集」★ |

最后一行很重要：快照的失败模式是静默的，**必须主动把它变成明确的提示**。
注意措辞——实测表明缓冲区有 19 万行（§2.2），所以**不要假定它一定失败**，
只在「确实没找到目标」时才提示，避免误导用户。

## 4. 功能设计

### 4.1 主界面

（`ComponentActivity` + Compose + `LazyColumn`）。

#### 4.1.1 为什么只有一个「刷新」按钮

**数据源由状态决定，不暴露给用户**：

| 状态 | 「刷新」读哪里 | 命令 |
|---|---|---|
| `IDLE` | logcat 缓冲区 | `logcat -d -T n` |
| `CAPTURING` | **采集文件尾部** | `tail -n $n $CAPTURE_FILE` |
| `STALE` | 不读，走提示 | — |

初稿曾并列「抓取一次」与「刷新」两个按钮——**这是把内部状态泄漏到 UI**：
用户不该关心数据从哪来，两个按钮只会让人问「该点哪个」。

**⚠️ 命令执行期间禁用「刷新」按钮**（不是排队）。
实测已知 Shizuku 通道是**同步阻塞**的（`IShizukuUserService.exec`），
并发发起多个 `exec` 会互相干扰。用单一 in-flight 标志位控制。

##### 4.1.3 ⚠️ 读取方式：全文件检索，不是「读末尾 N 行」★

> 🔴 **2026-09-19 修订。** 原实现是 `tail -n N`，存在一个**让工具基本不可用**的缺陷。

**实测数据**（用户报的问题）：

| 项 | 值 |
|---|---|
| 某高频 TAG 的速率 | 1000 行 / 0.352 秒 ≈ **2841 行/秒** |
| 每行长度 | 约 140 字符 |
| 写入速率 | ≈ **400 KB/秒** |
| 原轮转配置 `-r 1024 -n 3` 的总容量 | 4 MB → 只能覆盖 **约 10 秒** |
| `tail -n 1000` 覆盖的时长 | **0.35 秒** |

用户的采集区间是 5 分钟，其中目标日志出现在采集开始后 16 秒——
**既被轮转覆盖了，也远超"末尾 1000 行"的范围**。

**两道闸门各缩水一次，且都没有任何提示**，用户只能得出「这工具漏日志」的结论。

##### 修法

| 项 | 原 | 现 |
|---|---|---|
| 轮转容量 | `-r 1024 -n 3`（4MB） | `-r 65536 -n 4`（256MB ≈ 10 分钟） |
| 读取 | `tail -n N $CAPTURE_FILE` | `cat $(ls -tr $CAPTURE_FILE*) \| grep -e RE \| tail -n N` |
| 过滤位置 | 读回来再内存筛 | **下推到 grep** |
| 覆盖范围 | 不显示 | 底部显示「实际覆盖 HH:MM:SS–HH:MM:SS」 |

##### 三个实现要点

1. **必须用 `ls -tr` 排序，不能直接 cat 通配符**。
   轮转文件名是 `.1` `.2` … `.10`，shell 通配符按**字典序**展开时
   `.10` 会排在 `.2` 前面 → 输出乱序。
2. **`grep -a` 不是可选的**。日志里混进二进制字节时 grep 会判定
   "binary file matches" 而不输出内容 —— 表现是"搜到了但什么都没有"。
3. **用户输入必须转义正则元字符**。TAG 里的 `.` 不转义会变成"任意字符"，
   匹配结果莫名其妙地变多。（实现时真的写错过一次：
   Kotlin 里 `"\$0"` 是字面量 `$0` 而非正则反向引用。）

##### ⚠️ 由此带来的取舍

过滤下推到 shell 后，**改过滤条件要重跑一次命令**（原先是内存重筛）。
所以界面上那个按钮由「刷新」改名为「**检索**」——语义更准确，
也让用户知道点一下会执行一次查询。

这个取舍是必要的：采集文件可达数百 MB，不可能整个读回来；
而"读末尾 N 行再筛"正是上面那个缺陷的根源。

##### 仍然不能保证「覆盖整个采集区间」

轮转容量只是把窗口拉长。写入速率不可预知，**超过容量就会丢早期内容**。
所以这不是"修好了"，而是"能覆盖多少覆盖多少，且**明确告诉你覆盖了什么**"。

### 4.1.2 底部状态必须区分数据源 ★

两种数据源的**语义不同**，文案必须写出来：

| 数据源 | 会变吗 | 含义 |
|---|---|---|
| **缓冲区**（空闲） | ⚠️ **会变** | 滚动窗口，「此刻最近 N 行」。两次刷新结果**可能不同** |
| **采集文件**（采集中） | ❌ **不变** | 从开始到停止之间的日志，刷新多少次都是同一批（除非还在继续采集） |

采集中额外显示**时间范围**（文件首行↔末行的时间戳），用户据此知道「这批覆盖哪段时间」——
这直接对应「我第 1 秒开、第 10 秒关，拿到的就是这 10 秒」的心智模型。

**列表用「替换」而非「累积」**：每次刷新显示数据源的完整快照。
累积在此处毫无价值（采集态数据本来就不变；快照态想凑更长窗口应直接调大条数），
反而会让用户困惑「这行怎么出现了两次」。

##### 4.1.4 ⚠️ 采集完成后不能再读缓冲区 ★

> 🔴 **2026-09-19 修订。** 用户报：「点不同 TAG 切换过滤时，刷新到了非采集期间的日志。」

**根因**：三态机（`IDLE`/`CAPTURING`/`STALE`）里**缺一个「采集已完成」状态**。
停止采集后 `buildStopCapture` 删掉 pidfile → 状态判定退回 `IDLE` →
而 `IDLE` 的数据源是**实时滚动的缓冲区**。采集文件还在盘上，但已经没人读了。

于是用户切 TAG 触发的刷新，读到的是"现在"的日志，不是刚采的那批。

**修法**：加 `CaptureState.Completed`，用**标记文件**（`logcat_capture.done`）持久化。

| 状态 | 数据源 | 会变吗 | 刷新按钮 |
|---|---|---|---|
| `IDLE` | logcat 缓冲区 | ⚠️ 会（滚动窗口） | 需要 |
| `CAPTURING` | 采集文件 | ⚠️ 会（在增长） | 需要 |
| **`COMPLETED`** | 采集文件 | ❌ **不会（已固定）** | **隐藏** |
| `STALE` | 上次采集文件 | ❌ 不会 | **隐藏** |

⚠️ **用文件而非内存标志**：与 pidfile 同一个理由 ——
采集脱离 UI 存活，App 被杀后重进也该看到同一批（§4.2.1）。

⚠️ **探测顺序：先看进程，再看标记**。反过来的话，一次新采集刚开始
（pidfile 已写、done 标记还没来得及删）会被误判成"已完成"，
用户看到的是上一批日志。所以 `buildStartCapture` 里也加了 `rm -f $DONE_FILE`。

##### 4.1.5 ⚠️ grep 必须带 `-E` ★

> 🔴 **2026-09-19 修订。** 用户报：「采集不到日志，但别的工具能看到有」

`buildSearchPattern` 产出的 pattern 用的是 **ERE 语法**（`[ ]+`、`.*`、`|`），
而拼出的命令是 `grep -ai -e '...'` —— **没有 `-E`**。

在基本正则（BRE，grep 默认）下 **`+` 是字面字符而不是量词**，
所以 `[ ]+` 去匹配"一个空格后跟一个加号"，**永远匹配不到任何行**。

实测：

| 命令 | 结果 |
|---|---|
| `grep -ai -e '[ ]+[IWEF][ ]+...'` | 退出码 1，未命中 |
| `grep -aEi -e '...'` | 命中 |

**这个失败模式极其误导**：采集文件好好地写着日志、命令正常返回、
**没有任何报错**，只是永远搜不到东西。看起来完全像"采集没工作"。

**为什么旧测试没拦住**：原断言只检查了 `grep -a`（那是为二进制字节问题加的），
**没检查 `-E`**。已补两条断言。

##### 4.1.6 ⚠️ `cat $(ls …)` 无匹配时会挂死 ★★

> 🔴 **2026-09-19 修订。** 用户报：「点开始后界面一直显示刷新中，
> 连停止按钮都变灰点不动，必须退出重进。」

**这是本条链路里最严重的一个，因为它会让整个界面失去响应。**

检索命令是：

```bash
cat $(ls -tr $CAPTURE_GLOB 2>/dev/null) | grep ...
```

当通配符**无匹配**时，`$(...)` 展开为**空串**，命令退化成**裸 `cat`**。
而 `cat` 不带文件参数时**读标准输入** —— 在 `exec` 通道下 stdin 不关闭，
于是**命令永不返回**。

**触发时机**：刚点「开始采集」时。`buildStartCapture` 会先执行
`rm -f $DONE_FILE $CAPTURE_GLOB`（清理上一轮），而 logcat 还没创建新文件 ——
那一刻检索正是无匹配。

**连锁反应**：`refreshing` 永真 → 界面一直"刷新中" →
`canStop` 里检查了 `refreshing` → **停止按钮变灰** → 退出重进才恢复。

**修法**：`cat $sources </dev/null`。裸 cat 立刻读到 EOF 返回空。
同类问题一并修了 `buildCaptureSize`（无匹配时 `du` 也会读 stdin）。

> ⚠️ **两个改动叠加才出现**：`rm -f $CAPTURE_GLOB`（清理旧轮转份）
> 与 `cat $(ls …)`（检索）单独任何一个都不会触发。
> 这类"只在特定时序下出现"的 bug，靠读代码很难发现 ——
> 要问「这个命令在最坏输入下会怎样」。

### 4.2 采集状态机

```
        ┌──────────┐  点「开始」   ┌──────────┐
        │  空闲    │ ───────────► │  采集中  │
        │  IDLE    │              │CAPTURING │
        └──────────┘ ◄─────────── └──────────┘
              ▲        点「停止」/ 到时长上限
              │                            │
              │    ┌──────────┐            │
              └────│  STALE   │ ◄──────────┘  进程意外死亡
                   │ 脏状态   │              （App 被杀 / 崩溃）
                   └──────────┘
                        │ 用户点「清理」
                        └──► IDLE
```

#### 4.2.1 状态判定：不能只靠内存标志 ★

§4.2 边界 2 决定了**判定必须可持久、可重建**——
App 被杀后 shell 侧的 logcat 还在跑，内存里的 `StateFlow` 早就没了。

**判定来源：pidfile + 进程存活**，一条命令拿全部：

```bash
if [ -f $PID_FILE ]; then
  pid=$(cat $PID_FILE)
  if ps -A -o PID= | grep -qw "$pid"; then
    echo "CAPTURING pid=$pid"
  else
    echo "STALE pid=$pid"        # pidfile 在但进程没了 → 脏数据
  fi
else
  echo "IDLE"
fi
```

**三态而非两态，`STALE` 是必须单独处理的第三种**：

| 状态 | 判定 | 处理 |
|---|---|---|
| `IDLE` | pidfile 不存在 | 正常空闲 |
| `CAPTURING` | pidfile 存在 **且** 该 pid 存活 | 采集态 |
| **`STALE`** | pidfile 存在 **但** pid 不存活 | ⚠️ **提示「上次采集异常结束」+ [清理] 按钮**（删 pidfile），**不自动删**——用户可能想看看那次的日志 |

> ⚠️ **必须按 pidfile 精确匹配，不能用 `grep logcat`**。
> 实测印证：`D.3b` 两轮分别数到 3 和 1 个 logcat 进程——
> **可见性本身还受执行身份影响**，该指标不能用于判定。

**判定的调用时机**：

| 时机 | 用途 |
|---|---|
| `onCreate` / `onResume` | 恢复现场（含"离开后回来"） |
| 点「开始」前 | 防重复启动（边界 5） |
| 点「刷新」前 | **决定数据源**（§4.1.1） |
| 每 N 秒（可选） | 检测采集意外死亡 → 转入 `STALE` |

#### 4.2.2 其余边界

| # | 情况 | 处理 |
|---|---|---|
| 1 | 用户离开 Activity | 采集**继续**，回来时按 §4.2.1 恢复显示 |
| 2 | App 进程被杀 | → `STALE`（§4.2.1） |
| 3 | 时长上限到 | **双保险**：App 侧计时即时 `kill` + 提示；即使 App 已死，shell 侧 `timeout`（§4.7）也会到点结束进程 |
| 4 | 开始采集失败 | 明确报错（Shizuku 未授权 / 无权限），**不静默** |
| 5 | 重复点「开始」 | 先跑 §4.2.1 判定 |

⚠️ 第 1、2 条是本方案**特有的复杂点**——因为采集不依赖 UI 存活。
好处是「可以后台采」，代价是必须**用 pidfile 做状态锚点**。
**这是与纯快照方案相比新增的复杂度，要认。**

#### 4.2.3 ⚠️ 实现控制器时踩出来的三个坑 ★

> 2026-09-18 实现 `LogcatCaptureController` 时发现。**三条都不报错、只静默失效**，
> 因此都补了单测或写进了代码注释。

| # | 坑 | 症状 | 正确做法 |
|---|---|---|---|
| 1 | **`StateFlow` 用 `equals` 去重** | 用"重复赋 `session` 同一个实例"来驱动界面重算时长 → **正计时停住不动**（赋同一实例不发射） | 时间由**独立的 `nowMs` 流**承载，每秒推一个新值 |
| 2 | **探到 `STALE` ≠「异常结束」** | shell 侧 `timeout` 到点结束后，pidfile **仍在**（`echo $!` 写的是 `timeout` 自己的 pid，它退出后该 pid 查不到）→ 自然收尾也被报成"上次采集异常结束" | 按**「是否已到自己设的上限」**区分：到了 = 正常收尾，没到却死了 = 异常（被系统杀） |
| 3 | 自动停止在 ticker 协程里 `cancel()` 自己 | 当前恰好没踩到（cancel 后无挂起点），但**极脆弱**——以后在 `stop()` 后加任何挂起代码都会被静默跳过 | 自动停止**另起协程**执行 |

**坑 2 的推演**（第 2 条最反直觉，值得展开）：

```
timeout N logcat ... & echo $! > pidfile
                        └─ 写的是 timeout 的 pid，不是 logcat 的

到点 → timeout 杀掉 logcat、自己也退出 → pidfile 里的 pid 已不存在
     → 下次探测得 STALE（而不是 IDLE，因为 pidfile 没人删）
```

若只把 `STALE` 当异常，则**每一次到点自动停止都会留下一条假的「上次异常结束」提示**，
用户下次进来看到会以为出了问题。所以探测到进程消失后，还要看
`CaptureSession.hasReachedLimit(now, timeoutSec)`：

| 探测结果 | 已到自己设的上限？ | 判定 | 处理 |
|---|---|---|---|
| `IDLE` | — | 用户手动停的（`buildStopCapture` 删了 pidfile） | 静默转出 |
| `STALE` | ✅ | **正常收尾**（shell 侧 `timeout` 到点） | `stop()` 清掉 pidfile + 提示"已到达时长上限" |
| `STALE` | ❌ | **异常**（进程被系统杀） | 转 `STALE` 态，提示"上次采集异常结束" |

⚠️ 正常收尾那一路**必须走 `stop()` 而不是直接置 `Idle`**——
`stop()` 会 `rm` pidfile，而直接置 `Idle` 会把 pidfile 留在盘上，
下次进界面又探到 `STALE`，假提示卷土重来。

> **附带结论**：`buildStopCapture()` 里的 `rm -f $PID_FILE` 不只是"清理"，\
> 它还是**收尾与异常的唯一分界线**。不要因为"kill 已经成功了"就把它去掉。

### 4.3 命令构造（纯函数）

```kotlin
object LogcatCommands {
    /** 跨进程单次传输的硬上限，防撞 Binder IPC 限额（§2.1） */
    const val MAX_LINES = 2000

    /** 采集文件与 pidfile 路径 */
    const val CAPTURE_FILE = "/sdcard/vFlow/logs/logcat_capture.log"
    const val PID_FILE     = "/sdcard/vFlow/temp/logcat_capture.pid"

    /**
     * ⚠️ `>/dev/null 2>&1 </dev/null` **不是可选的**（§2.1b）。
     * 后台 logcat 会继承 shell 的 stdout → 管道不关闭 →
     * ShizukuUserService 的 readStream 等不到 EOF → **整个 exec 永久挂起**。
     * 实测踩过（探针第二轮无输出挂死）。
     */
    fun buildStartCapture(rotateKb: Int = 1024, rotateCount: Int = 3): String =
        "/system/bin/logcat -v threadtime -r $rotateKb -n $rotateCount -f $CAPTURE_FILE " +
        ">/dev/null 2>&1 </dev/null & echo \$! > $PID_FILE"

    fun buildStopCapture(): String =
        "kill \$(cat $PID_FILE) 2>/dev/null; rm -f $PID_FILE"

    /** 清理脏状态（§4.2.1 的 STALE 态，用户手动点「清理」） */
    fun buildClearStale(): String = "rm -f $PID_FILE"

    /**
     * 状态判定（§4.2.1）。输出恒为一小行，不会撞 §2.1 的 Binder 上限。
     * ⚠️ 用 pidfile 精确匹配，**不要用 `grep logcat`**（实测该指标不可靠）。
     */
    fun buildProbeState(): String =
        "if [ -f $PID_FILE ]; then " +
            "pid=\$(cat $PID_FILE); " +
            "if ps -A -o PID= | grep -qw \"\$pid\"; then echo CAPTURING:\$pid; " +
            "else echo STALE:\$pid; fi; " +
            "else echo IDLE; fi"

    /** 从文件尾部有界读取（采集态） */
    fun buildTail(lines: Int): String =
        "tail -n ${lines.coerceIn(1, MAX_LINES)} $CAPTURE_FILE"

    /** 快照（非采集态） */
    fun buildSnapshot(lines: Int, tag: String?, minLevel: Char): String {
        val n = lines.coerceIn(1, MAX_LINES)
        return buildString {
            append("/system/bin/logcat -d -v threadtime -T ").append(n)
            tag?.takeIf { it.isNotBlank() }?.let {
                append(" -s ").append(shellQuote(it)).append(":").append(minLevel)
            }
        }
    }

    /** TAG 统计专用的快照：**绕过 TAG 过滤**（见 §4.5） */
    fun buildSnapshotForTagStats(lines: Int, minLevel: Char): String =
        "/system/bin/logcat -d -v threadtime -T ${lines.coerceIn(1, MAX_LINES)}" +
            if (minLevel != 'V') " *:$minLevel" else ""
}
```

**设计要点**：

1. **`/system/bin/logcat` 绝对路径**——app_process / sh 环境下的 `PATH` 不确定（触发器设计 §6.6 同理）。
2. **`-f <file>` 而非管道重定向**：logcat 自己带轮转（`-r`/`-n`），不用自己实现。
3. **调试工具**的 TAG 过滤**可以下推**（用 `-s`）——因为没有热更新需求，命令只在点击时生成一次。
   这与触发器设计 §5.3「有意不下推」不冲突，**两者场景不同**。
4. ⚠️ **「排除本应用日志」不要下推**：`--pid` 是**白名单**语义，用不上；
   而 `grep -v` 会让用户无法事后切换。**改为抓全量 + App 侧按 pid 过滤**，可随时切换显示。
5. ⚠️ **采集文件永远不带过滤写**——全量写入，过滤在 App 侧做（§4.1.1）。
   这样改过滤条件只需重渲染，不用重跑命令，也支持事后切换。
6. **刷新分流的调用方**（§4.1.1）：

   ```kotlin
   val cmd = when (state) {
       IDLE      -> buildSnapshot(lines, tag, minLevel)
       CAPTURING -> buildTail(lines)      // 过滤在 App 侧
       STALE     -> null                  // 不执行，走提示
   }
   ```

### 4.4 解析层（与触发器共用）

```kotlin
// 与 logcat-trigger-design.md §5.1 完全同一份实现
val THREADTIME = Regex("""^(\d{2}-\d{2})\s+(\d{2}:\d{2}:\d{2}\.\d+)\s+(\d+)\s+(\d+)\s+([VDIWEF])\s+(.+?)\s*:\s?(.*)$""")

/**
 * @param prev 上一条成功解析的行；降级时继承其 tag/level（触发器设计 §5.1）
 */
fun parseThreadtime(line: String, prev: ParsedLine?): ParsedLine
```

⚠️ **降级语义必须与触发器设计 §5.1 一致**：无前缀行**继承上一条的 tag/level**，
而不是置空 / 置 `V`（后者会让 `min_level` 把它过滤掉，等于丢行）。

#### ⚠️ 日志头标记行必须单独识别（实测新增）

`logcat -d` 的输出里**混有非日志行**：

```
--------- beginning of main        ← 类别分隔标记，不是日志
--------- beginning of system
--------- beginning of crash
```

**实测证据**（§2.4）：`-T 5` 返回 7 行、`-t 5` 返回 6 行——**`-T n` 不保证恰好 n 行**。
多出来的就是这些标记行。

**两个必须处理的点**：

1. **解析时要识别并跳过**（或单独标记），否则它们会走降级路径被当成"续行"，
   污染上一条的 tag/level 继承链。
2. **不要假定「`-T n` 返回 n 行」**——工具里的"条数"设置是**上界，不是精确值**。

建议在 `parseThreadtime` 之外单列一个判定：

```kotlin
private val BUFFER_MARKER = Regex("""^-{5,}\s*beginning of .+$""")

fun isBufferMarker(line: String): Boolean = BUFFER_MARKER.matches(line.trim())
```

**本工具的价值在于把降级显式化**：

| UI 呈现 | 含义 |
|---|---|
| `↳` 前缀 + 灰色 | 该行是降级行（无 TAG 前缀，多为多行日志的续行） |
| 底部「降级 N 行」 | 直接告诉用户「有 N 行没有 TAG 前缀，你的 message 条件可能因此失配」 |
| 头标记行 | 建议**直接过滤掉不显示**（对调试无价值），或折叠成一行分隔线 |

**这个提示能提前暴露触发器最隐蔽的坑**：用户配了 `message contains 'xxx'` 却不触发，
原因往往是那行是降级行。在调试阶段看到，比触发器做完后排查便宜得多。

### 4.5 TAG 统计（最实用的功能）

用户通常不知道该过滤哪个 TAG。点「TAG 统计」后抓一批日志，App 侧按 TAG 聚合：

```
MyApp              234 行
ActivityManager     89 行
WindowManager       45 行
```

点某行即把该 TAG 填入过滤框。

#### ⚠️ 必须绕过当前的 TAG 过滤 ★

**这是本功能能否成立的关键**，也是初稿没想清楚的点。

用户点「TAG 统计」的动机恰恰是**「我不知道该过滤哪个 TAG」**——
此时他要么没设过滤，要么设的是**猜的**。
**用被猜过的条件去统计，等于让用户自己回答自己的问题。**

| 条件 | 统计时是否生效 | 理由 |
|---|---|---|
| **TAG 过滤** | ❌ **必须绕过** | 否则统计结果只有用户已填的那个 TAG，毫无意义 |
| 级别过滤 | ⭕ **可保留** | 「只看 W 以上有哪些 TAG」是合理诉求 |
| 条数 | ✅ 保留 | 决定采样量 |

因此 `buildSnapshotForTagStats()`（§4.3）**不带 `-s`**，只带级别。

#### 采样源同样按状态分流（§4.1.1）

采集态下应从**采集文件**读取，而不是缓冲区——否则用户会奇怪
「我明明在采集，统计出来怎么没有刚才那条」。

**放在 App 侧聚合**：数据已经传过来了，再让 shell 跑 `awk` 反而多一次跨进程往返。

### 4.6 快照为空时的引导

```kotlin
if (lines.isEmpty() && state == IDLE) {
    // 不要只说「没有日志」——要说清楚可能的原因与下一步
    showHint("未读到日志。logcat 缓冲区可能已轮转，建议开启「采集」后复现问题。")
}
```

这是 §2.2 那个**静默失败**的对策。

**各类空/异常态需分别给文案**（不要一律「没有日志」）：

| 状态 | 文案要点 |
|---|---|
| `IDLE` + 空 | 「未读到日志。可能已被轮转，建议开启『采集』后复现问题。」 |
| `CAPTURING` + 空 | 「采集刚开始，还没有日志产生。」（**不是错误**，别报错） |
| `STALE` | 「上次采集异常结束（App 可能被系统回收）。[清理]」 |
| Shell 未就绪 | 「需要 Shizuku 或 Root 权限才能读取系统日志。」+ [去授权] |
| 命令 `TIMEOUT` | 「命令超时（N 秒）。可能是日志量过大，试试调小条数。」 |

### 4.7 时长上限：必须下推到 shell 侧 ★

> 🔴 **本节 2026-09-18 新增。** 原设计只在 App 侧计时，存在一个真实漏洞。

**漏洞**：App 侧的"时长上限"计时只在 App 活着时有效。而采集恰恰设计成
**脱离 UI 存活**（用户可以离开 App 去复现问题）——此时若 App 被系统杀掉，
计时器随之消失 → **logcat 会无限期跑下去**。

也就是说：**「防忘记关」的机制，在最容易忘记关的场景下失效。**

**修法**：把时限下推到 shell 侧，进程自己带超时。

```bash
timeout 300 /system/bin/logcat -v threadtime -r 1024 -n 3 -f $CAPTURE_FILE \
  >/dev/null 2>&1 </dev/null & echo $! > $PID_FILE
```

| 场景 | App 活着 | App 被杀 |
|---|---|---|
| 到点 | App 侧停 + UI 即时反馈 | **shell 侧 `timeout` 停** ✅ |
| 之后 | — | 进程消失，`ps` 查不到 → 下次进入判为 `STALE`（提示清理，§4.2.1） |

**两层不冲突**：App 侧计时负责 UI 显示与即时停止；shell 侧 `timeout` 是兜底。

`timeout` 是 toybox 自带的（项目内已有用例：`FileOperationModule.kt:1050` 用过
`toybox` 的 fallback 写法）。

⚠️ **`timeout 0` 在 toybox 里表示"不超时"**，与用户意图（尽快停）相反，
因此 `buildStartCapture` 里做了 `coerceAtLeast(1)`。

**界面上的计时是正计时**（`02:31` = 已采集多久），不是倒计时——
上限可调，倒计时会随改动跳变；且"我采了多久"比"还剩多久"更符合直觉。

## 5b. 超级岛通知（采集进行中的状态展示）

> ✅ **2026-09-18 已实现并真机验证通过。** 实现在 `services/island/` 的
> `IslandTemplate.kt` / `IslandTemplateBuilder.kt` / `IslandNotifier.kt`，
> 单测 `IslandTemplateBuilderTest.kt`（24 例）。

### 5b.1 需求

采集是**脱离 UI 存活**的（用户可以离开 App 去复现问题），
因此需要一条**离开 App 也能看见**的状态展示：

- 岛上有**正计时**（已采集多久）
- **计时器动图**（秒表动画）
- **结束按钮**（不用回 App 就能停）

### 5b.2 两条通道：不是两套体系，是同一份内容的两种投递

| 方式 | extras key | 结构 | 视图来源 |
|---|---|---|---|
| **模板** ← 本功能用这条 | `miui.focus.param` | `param_v2` 包裹 | SystemUI 按官方模板渲染 |
| 自定义 | `miui.focus.param.custom` | 扁平 | 应用提供的 `miui.focus.rv` |

**选择模板通道的理由**：只有它提供**系统原生计时器**（`timerInfo`）
和**内置 Lottie 动画**。RemoteViews 通道给不了这两样
（mindfs 曾在 rv 里放自定义动画，实测 SystemUI 只取静态首帧）。

⚠️ **本功能只写 `miui.focus.param`，不写 `param.custom`、不写 `rv`**——
一旦写了 rv，SystemUI 会走自定义视图分支，计时器与动图都不会渲染。

### 5b.3 ⚠️ 踩出来的坑（每条都不报错、只是静默失效）

| # | 坑 | 症状 | 正确做法 |
|---|---|---|---|
| 1 | **`autoplay` 默认 false** | 图标出来了但是**静止的** | 显式写 `"autoplay": true`（运行态），暂停态写 `false` |
| 2 | **岛按钮的接收器必须静态注册** | 按钮渲染正常、点着没反应 | `AndroidManifest.xml` 静态注册 + **显式 Component 意图**（照 `WorkflowActionReceiver`）。动态注册的接收器在用户点击时早已注销 |
| 3 | **`timerInfo` 要写三处** | 某处不显示计时 | `highlightInfo` / `sameWidthDigitInfo` / `animTextInfo` 各写一份，**不要"优化"成一处**——SystemUI 读哪处未经证实 |
| 4 | `islandTimeout` 单位是**秒**，通知 `timeout` 是**分钟** | 岛提前消失 | 别弄混 |
| 5 | 按钮广播需 `FLAG_RECEIVER_FOREGROUND` | 后台可能延迟投递 | 官方要求；`IslandNotifier` 内部统一加，调用方不必管 |
| 6 | **按钮要幂等** | 用户连点 5 次触发 5 次 | 实机验证时连点确实收到 5 次广播，生产实现需容忍重复触发 |

### 5b.4 真机验证结论（2026-09-18）

| 验证项 | 结果 |
|---|---|
| 岛出现、图标显示 | ✅ |
| 秒表动图播放 | ✅ **内置 Lottie 在第三方可用**（文档原标注「未验证」） |
| 正计时走动（`timerType=1`） | ✅ |
| 暂停态定格（`timerType=2` + `autoplay=false`） | ✅ |

| **结束按钮点击回传** | ✅ 修正坑 2 后（连点 5 次收到 5 次广播） |

### 5b.5 通用性设计

`IslandTemplate` **不含任何业务语义**（没有 workflow / logcat 字段），
只有「图标 + 文本 + 计时器 + 按钮」。将来任何需要"岛上走动的计时器"的
功能（某个耗时模块、录音类功能）都可直接复用，
只需填一个 `IslandTemplate` 调 `IslandNotifier.show()`。

**与工作流执行通知互不干扰**：后者走自定义通道（rv），本层走模板通道，
各写各的 extras key，通知 id 也分开（本层用 `97100` 起，
避开工作流的 `[100000, 150000)` 与既有 `97010`）。

### 5b.6 采集侧的接线（2026-09-18 实现）

在 `LogcatCaptureController.applyState()` 里集中联动——**所有状态变更都走这一个出口**，
避免出现「状态变了但岛没跟上」：

| 状态 | 岛的动作 |
|---|---|
| → `CAPTURING` | `show()`：`stopwatch_big` 动图 + 正计时（`COUNT_UP_RUNNING`）+ 「结束」按钮 |
| → `IDLE` / `STALE` | `cancel()`。**无条件调用**，不记录"是否发过岛"的标志——`cancel` 对不存在的通知是安全的，比维护一个标志更不容易漏 |

**两处刻意的设计选择**：

1. **岛不每秒重发通知**。`timerInfo.timerWhen` 是计时起点，SystemUI 自己往前走。
   每秒重发纯属浪费，且会让通知栏闪。
2. **岛存活比采集上限长 60 秒**（`LogcatCaptureUi.islandTimeoutSec`）。
   理由是自愈：App 若被杀，采集由 shell 侧 `timeout` 结束，
   但**没有任何人再去取消岛**——让它比上限晚一点自动消失是唯一的手段。

⚠️ 「结束」按钮的 `Intent` **必须是显式 Component**，指向 Manifest 静态注册的
`LogcatActionReceiver`（§5b.3 坑 2）。接收器内部用 `goAsync()` 延长生命周期——
`onReceive` 返回后进程可能被回收，而停止采集是一次跨进程 shell 调用。
按钮幂等由 `LogcatCaptureController.stop()` 保证（实测连点 5 次收到 5 次广播）。

## 11. 与「启用调试日志」开关的关系

⚠️ **本工具不依赖那个开关。** 但需要明确区分，避免实现时被名字带偏。

设置页有个「启用调试日志」（`debugLoggingEnabled`），它控制的是 **vFlow 自己的调试日志**
（`DebugLogger` 的 `logBuffer`，上限 5000，见 `DebugLogger.kt:160-167`）。
`getLogs()` 读的正是这个 buffer，所以**导出应用日志**受它控制。

**但本工具的数据源是设备日志，与它无关**：

| | 数据来源 | 经过 `DebugLogger` 吗 |
|---|---|---|
| **logcat 查看器** | `logcat`（shell）→ `exec` 返回 → 解析 → UI | ❌ **不经过** |
| **触发器** | Core 侧匹配 → socket 推送 → `triggerData` | ❌ **不经过** |

> ℹ️ 另有 `crashBuffer`（上限 200）**无条件写入**，`getRecentLogsForCrash()` 可取——
> 但那是崩溃上报用的通道，与本工具无关。

#### ⚠️ 但调试触发器时，用户两个都需要

这是**用户容易混淆**的地方，值得在 UI 上做一点引导：

| 用户想看什么 | 数据源 | 受开关控制 |
|---|---|---|
| 设备打了什么日志（触发器该不该命中） | **本工具** | ❌ |
| 触发器有没有触发、匹配到什么 | `DebugLogger` | ⚠️ **是** |

**建议（可选增强）**：本工具检测到 `debugLoggingEnabled=false` 时，
给一句提示「开启『调试日志』后，可同时看到 vFlow 自身的触发记录，便于对照」。

**这是加分项，不是必需**。属实现时可选。
