vFlow · Chat 悬浮窗 UI 原型（可交互）

核心场景：AI 通过无障碍在目标 App 里操作，操作本身你看得见；但它「在说什么」原本留在 Chat 页里。
悬浮窗要做的事，就是把 AI 说的话随身带走——你跟着 AI 走到哪，都还听得到它。

折叠态要点

  • 显示 AI 说的话：没找到深色模式，我去「显示」里找 这类过程说明，是用户跟着 AI 离开 Chat 页后最容易丢的信息。
  • 无助手文本时才退化为动词状态（如「正在观察…」），而不是反过来。
  • 待审批徽标：有 PENDING 操作时窄条出现橙色标记，避免折叠时漏掉。
  • 可拖动 + 吸附：拖到屏幕右/左边缘松手会贴边，把操作区域让出来。
  • 半透明：约 0.92 alpha + 高斯模糊，减少遮挡感。

② 展开态 —— 完整对话面板 点折叠条展开。消息列表 + 输入框；输入框最多 6 行；Agent 运行中发送键变「停止」。

展开态要点

  • 消息与 App 内完全同源：同一个 ChatViewModel 实例，这里发的回到 App 里照样看得到。
  • 工具调用可见：observe_screen / click 以轻量卡片呈现，不展开完整参数。
  • 运行中发送 = 排队：不打断当前任务，显示「已排队 N 条」。
  • 头部不提供会话切换、历史、预设切换（非目标，避免把完整 Chat 页塞进小窗）。
  • 尺寸约 344×500，内容超出滚动，不固定撑满。

审批要点

  • 窗内直接审批，不跳回 App —— 这是「边看边操作」的关键，否则一切回 App 就前功尽弃。
  • 卡片显示 工具 id + 风险等级 + 参数摘要；高风险（HIGH）用红色标记。
  • 缺系统权限时（如截图需 MediaProjection）会拉起一个透明中转页请求授权，返回后自动继续，用户无感。
  • 只弹一次：悬浮窗与 App 内 Chat 页会同时观察审批请求，需有归属仲裁（设计文档 §5.3.3），否则会重复弹窗。
  • Agent 运行中审批按钮应禁用，与 App 内的约束对齐。

输入与键盘要点

  • 焦点是难点：overlay 窗口默认 FLAG_NOT_FOCUSABLE，收不到输入。点输入框时要去掉该 flag，且 Compose 侧需重新发起一次焦点请求，否则会「点了没反应」。
  • 键盘避让：overlay 不在标准 inset 分发链上，imePadding() 不可靠。计划监听 IME inset 手动上移窗口（本原型演示的就是上移效果）。
  • 失焦恢复：收起键盘后窗口恢复不可聚焦，避免长期抢占焦点影响被调试的 App。
  • 这两项都未经真机验证，已列入 P0 技术门槛。

⑤ 状态一致性 —— 关掉悬浮窗，回 App 里看 悬浮窗不是第二套会话。它和 App 内 Chat 页共用同一个状态：窗里说的、批的，回到 App 里一模一样。

为什么必须共用同一个 ViewModel

  • 若悬浮窗另建一个 ChatViewModel，就会变成两套会话：窗里说的话回到 App 看不到，反之亦然。
  • 方案是把它提到 Application 作用域（ChatViewModelHolder），App 与 Service 取到同一个实例。
  • 代价：VM 与进程同寿，onCleared() 不再触发，监听器不注销。这是有意为之，已在设计文档登记。
  • 顶栏的 ⧉ 是新增的悬浮窗入口，与「新对话」「历史」并列。

本原型仅表达交互与信息层级，颜色/间距以最终实现为准。
